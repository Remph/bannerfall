A patch release on top of 1.6.2. Closing the code sheet of a build plan no longer closes the plan editor, Enter starts a recruit order, guild mates have their own colour on the maps, and reports of your own villages offer "Re-recruit losses". A new version of the same 1.x shows a "Reload" strip instead of reloading the page under you, the map can show only the movements of the current village, and the village picture, the buttons and the menu got a little motion. For hosts, the admin page and `bannerfall-admin` can switch debug logs on while the server runs. No database migration and nothing to configure.

## What is new and fixed

**Village automation**
- **Plan codes:** pasting a code into the plan editor closed the whole editor when the code sheet closed (a sheet inside a sheet closed its parent). Only the code sheet closes now

**Recruiting and reports**
- **Enter recruits:** pressing Enter in a unit's number field starts the recruit order, as the button does
- **Re-recruit losses:** a battle report of one of your own villages has a "Re-recruit losses" button. It opens the village's plan sheet with the goal set to what the village has, plus what is queued, plus what the battle cost. Change a goal if you want fewer or more; the button recruits as far as the resources go right now. The goal you recruited is remembered for that report and village, so opening the report again doesn't ask for the loss twice

**Map**
- **Guild mates in their own colour:** villages of your guild mates are green (own villages stay red), with an entry in the legend, on the map and on the overview map
- **Movements of this village only:** the map's movement switch can show only the movements of the village you are in, which is the default. One switch shows all of them again, and each device remembers its choice. Incoming attacks on your other villages are hidden while it is on

**Updates**
- **New-version strip:** when the server was updated to a newer patch of the same 1.x, a dismissible strip says "A new version of Bannerfall is available. Reload to use it." and the page keeps running until you reload. A new minor or major version still reloads open pages by itself, as before

**Motion**
- Buttons give a little when pressed, menu rows come in one after the other, the farm, the headquarters and the smithy have chimney smoke, a building's level pops when it goes up, and the village picture has drifting cloud shadows and two birds. All of it stops when the device asks for reduced motion, and nothing needs a hover

## For hosts

- **No migration, nothing to configure.** No new settings or environment variables, no change to Caddy, `compose.prod.yaml` or `edge/`
- **Debug logs while the server runs:** the status card of the admin page has a switch "Debug logs", and `bannerfall-admin debug-log [on|off]` does the same (without a word it says how they are now). It sets the game's own logger to DEBUG and writes one line per handled event with its duration, one per battle and one per step of an NPC lord's round. Spring, Hibernate and Tomcat stay at INFO. Nothing is stored, so a restart is back to normal; every switch is written to the audit log. `server.log` no longer filters out the DEBUG lines (its size caps stay). Debug logs slow the server down and fill the files: switch them on to look into something, then off again
- **API:** `PUT /api/admin/debug-logging` with `{"enabled": true}`; `GET /api/admin/status` carries `debugLogging`. Nothing was removed
- **Automatic patch updates:** a world with `ops/bannerfall-auto-update` in its nightly cron line moves from 1.6.2 to 1.6.3 by itself once the image is published (backup, a five-minute warning in the chat, health check, rollback). `touch auto-update.hold` pauses it
- Open pages reload by themselves when the server moves to a new minor or major version (since 1.2.1); a patch shows the strip described above

## Upgrading a running world (from v1.6.2)

1. `git fetch --tags origin && git checkout v1.6.3`
2. `ops/bannerfall-update 1.6.3` (add `--build` if you build your images on the server). It takes the backup, warns the players, restarts a minute later and checks the new version. Only the app is recreated, and there is no migration
3. Several worlds behind the shared Caddy: update every world, then check out the same tag in the edge folder (`edge/` itself is unchanged)

Or by hand, as before: announce the update (`bannerfall-admin broadcast "Update in 5 minutes"`), take a backup (`ops/bannerfall-backup`), pull the image below or build it with `--build-arg VERSION=1.6.3`, set `BANNERFALL_IMAGE` in `.env` to it, `docker compose -f compose.prod.yaml up -d`, then check `bannerfall-admin status` (version 1.6.3) and `bannerfall-admin check`.

Going back to 1.6.2 is safe for the database, since there is no migration: set the old image and `git checkout v1.6.2`, then `up -d` again. Nothing saved by 1.6.3 breaks 1.6.2; the per-device choices (the movements switch, the recruited goals) simply aren't used by the older version.
