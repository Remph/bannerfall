A feature release on top of 1.4.1. Players get statistics (battle totals on every profile, three new ranking tabs and a daily history with charts) and push notifications on their phone or computer while the game is closed. Hosts can run several worlds on one server behind one shared Caddy, and let a world log in through an OpenID Connect account server, with one account for several worlds. It builds on v1.4.1 (and v1.4.0, which had no migration since); existing worlds keep running and update their database by themselves (migrations V44 to V47).

**Heads-up for running worlds:** the statistics count from the first start of 1.5 on. Nothing is reconstructed from old reports, so every player starts at zero and the profile says "Counted since …". Push notifications stay off until the host adds the world's key pair to `.env` (see *For hosts*); without it the Notifications page says this world sends none.

## What is new

**Statistics**
- Every profile, NPC lords' included, has a **Statistics** card: attacks and defences won and lost, enemy units killed attacking and defending, own units lost, loot taken and lost, villages conquered and lost, units recruited and building levels finished. Kills and losses count by **population**: a unit counts as much as the farm space it needs, so a noble weighs as much as 100 spearmen
- Only battles with a main battle count; a scout alone neither wins nor loses one, and an attack on your own village counts nothing. The killed attackers of a defence are shared by every defender in the village (the owner and each supporter) by the population each one brought; barbarians count nothing
- The ranking has three more tabs beside points: **Attacker** (killed attacking), **Defender** (killed defending) and **Plunderer** (loot taken)
- **Over time:** soon after midnight the server writes down the day that just ended. Every profile has a chart of the points or the villages per day, and the new **World statistics** page (linked from the ranking) shows the points of today's top five and the world's players, villages, barbarian villages and points over time. Today always shows live
- Statistics change nothing in the game: no rule, achievement or NPC lord reads them. Everyone in the world can see them, as the privacy page says

**Push notifications**
- Under **Notifications** in the menu a player turns them on for this device. Then the phone or computer shows a notification while the game is closed: an attack on one of your villages as soon as it is sent (with its arrival), a lost village, a private message, a guild invitation, the victory clock starting or stopping and the end of the world. A tap opens the right page
- Each kind has its own switch. **Build queue empty** is off by default: switched on, it sends one notification when a village's queue has run out, not one per building
- An attack train or a flood of fakes buzzes once rather than for every attack, and "Send a test" checks that it works
- On an iPhone or iPad it works only from the home screen (iOS 16.4 or newer); the page explains how. A logout, a password change or a ban removes the account's devices
- Notifications go out through the push service of each player's browser, encrypted so the service can't read them; no account anywhere else is needed

**Logging in through an account server** (off unless the host sets it up)
- A world can show a **"Log in with …"** button. In mode *linking* it stands next to the usual login, and players who already play here can link their account under **Change password**: from then on they log in at the account server with the same account on every world that uses it, keep their name here, and their password here stops working. In mode *required* the button is the only way in
- A first login through the account server asks for the world's invite code once (`/join`; links with `?invite=` fill it in), then founds the village. A name that is already taken on the world says how to link instead
- Bans and deleted players stay per world: a ban here also stops a player who logs in through the account server, and a ban or a deleted account at the account server ends the open sessions on the world at once (back-channel logout)
- **Careers:** with Bannerfall's own account server, a world can report its linked players' name, points, villages, rank, achievements, battle totals and, once the world ends, the result, for a career page there, and their profiles on the world link to it. Off by default; the privacy page says so when it is on

**Also changed**
- A visit without a login lasts 15 minutes instead of 30 days. A login still lasts 30 days without use, as before

## For hosts

- **Four database migrations**, run by Flyway on the first start. They only add tables and nullable columns, so they take moments:
  - V44: `account.external_issuer` and `external_subject` (the account server's account), `password_hash` may be empty for those
  - V45: table `career_sync` (what the world last reported for a career)
  - V46: tables `player_stat`, `player_day` and `world_day` (statistics)
  - V47: tables `push_subscription` and `push_preference`
- **Push notifications** need a key pair per world, made once (`docs/hosting.md` §14). The console makes it without a running server, so it can go into `.env` before the update and the app starts only once:
  ```
  docker run --rm --entrypoint bannerfall-admin <the 1.5.0 image> push keys >> .env
  ```
  (on a world already running 1.5: `docker compose -f compose.prod.yaml exec -T app bannerfall-admin push keys >> .env`, then `up -d`). Keep the two lines with the rest of `.env`: they are not in the database backups. A new pair later makes every device sign up again, by itself. `BANNERFALL_PUSH_SUBJECT` (optional) tells the push services how to reach you; empty, it is `BANNERFALL_OPERATOR_CONTACT` if that is an email address. The server must reach the push services over https. `bannerfall-admin status` shows how many devices get notifications
- **Several worlds on one server** (`docs/hosting.md` §12): each world keeps its own folder, database, `.env`, backups and token, and one shared Caddy (the new folder `edge/`, its own compose project on the host's network) holds ports 80 and 443 and passes each domain to its world's `APP_PORT`. A server with one world changes nothing. A second world sets its own `COMPOSE_PROJECT_NAME` and `APP_PORT` and leaves `COMPOSE_PROFILES` empty; §12.1 moves the first world behind the shared Caddy with a copy of its certificate, so the swap takes seconds and asks Let's Encrypt for nothing. Update every world to the same release, the newest first, then the shared Caddy
- **Account server** (`docs/hosting.md` §13, optional): register the world as a confidential client at an OpenID Connect provider (redirect `https://<domain>/login/oauth2/code/accounts`, PKCE, `preferred_username` in the ID token, back-channel logout to `/api/auth/backchannel-logout` recommended), then set `BANNERFALL_ACCOUNT_SERVER_ISSUER`, `_CLIENT_ID`, `_CLIENT_SECRET`, `_NAME` and `_MODE` (`OFF` by default, `LINKING`, `REQUIRED`) and `up -d`. `_CAREER=true` only for an account server that takes career reports. Switching a running world to `LINKING` changes nothing for existing players
- **New environment variables**, all optional and passed on by `compose.prod.yaml`: `BANNERFALL_ACCOUNT_SERVER_ISSUER`, `_CLIENT_ID`, `_CLIENT_SECRET`, `_NAME`, `_MODE`, `_CAREER`, and `BANNERFALL_PUSH_PUBLIC_KEY`, `_PRIVATE_KEY`, `_SUBJECT`; `COMPOSE_PROJECT_NAME` for a second world. Only one of the two push keys, or two that don't belong together, stops the app at the start. No change to the world's own `Caddyfile` or to `ops/`
- API: `GET /api/ranking?by=attacker|defender|plunderer`, `GET /api/players/{id}/history`, `GET /api/statistics/world`; `GET /api/push`, `PUT /api/push/subscription`, `POST /api/push/subscription/remove`, `PUT /api/push/preferences`, `POST /api/push/test`; `GET /api/auth/options`, `GET /api/auth/external`, `POST /api/auth/join`, `POST /api/auth/backchannel-logout`, `POST /api/me/link` (`{currentPassword}`); profiles carry `stats` and, for linked players, `careerUrl`. The web registers a service worker (`/sw.js`) for the notifications only; there is still no offline mode

## Upgrading a running world (from v1.4.0 or v1.4.1)

1. `git fetch --tags origin && git checkout v1.5.0` (a world on 1.4.0 gets the update script from 1.4.1 this way)
2. Pull the image below and add the push keys to `.env` (see *For hosts*), if you want notifications
3. `ops/bannerfall-update 1.5.0` (add `--build` if you build your images on the server). It takes the backup, warns the players, restarts a minute later and checks the new version (schema 47). Only the app is recreated
4. `bannerfall-admin status` shows the version and whether push is on

Or by hand, as before: announce the update, take a backup (`ops/bannerfall-backup`), pull the image or build it with `--build-arg VERSION=1.5.0`, set `BANNERFALL_IMAGE` in `.env`, `docker compose -f compose.prod.yaml up -d`, then `bannerfall-admin status` and `bannerfall-admin check`.

Going back to 1.4.x means restoring the backup taken before the update and starting the old image: the migrations can't be undone, and the statistics, devices and links since the update are lost with the play since then.

## Stack

Java 25, Spring Boot 4.1, PostgreSQL 18 (Flyway), React 19 with Vite, Docker Compose, Caddy. Web Push with the JDK's own cryptography (RFC 8291, VAPID), no extra service. Unchanged otherwise since v1.4.1.
