A small patch release on top of 1.3.0. Sending a report offers the players you last sent one to, the map draws less off screen while it moves, and the dependencies are up to date. It builds on v1.3.0; existing worlds keep running and update their database by themselves (one migration, V34).

## What is new

**Reports**
- **Recent recipients first:** the quick picks in a report's send sheet ("Recently contacted", up to 6) now start with the **last 3 players you sent a report to by name**, newest first, followed by the players of your inbox as before, with no name twice. A send to the guild doesn't count (it has its own button), nor a send that failed. Players you have blocked since and deleted accounts are left out; a recipient who deleted the copy still counts
- The picks appear once both lists are loaded, so none of them moves under a tap
- After the update the list starts from the reports already sent: for each player, everyone they ever sent a copy to, with the time of the newest one. Old copies don't record whether they went to the guild or to a name, so guild sends made before 1.3.1 can show up here once

**Map**
- Rivers, the map edge and movement lines are now cut to the visible area (plus a small margin) before they are drawn, instead of handing the whole path to the browser on every frame, often thousands of pixels off screen when zoomed in. This should stop the streaks some phones flashed across the map while it moved. The map looks exactly as before

**Under the hood**
- Web dependencies: `@stomp/stompjs` 7.4.0, `@tanstack/react-query` 5.104.2, `typescript-eslint` 8.71.2, `vitest` 5.0.4
- The GitHub Actions workflows use the current major versions of checkout, setup-node, pnpm/action-setup, setup-java and setup-gradle (the latter with its open-source `basic` cache)

## For hosts

- **One database migration**, run by Flyway on the first start: V34 adds the table `report_share_recipient` (sender, recipient, time of the latest send by name) and fills it from the report copies already sent, in one pass. It takes moments even on a world with thousands of reports
- No new settings, environment variables or admin commands, and no changes to the `Caddyfile`, `compose.prod.yaml` or `ops/`
- API: `GET /api/reports/recent-recipients` → `{names: [...]}`, the caller's last 3 recipients by name, newest first
- Open pages reload by themselves when the server version changes (since 1.2.1)

## Upgrading a running world (from v1.3.0)

1. Announce the update (`bannerfall-admin broadcast "Update in 5 minutes"`)
2. Take a backup (`ops/bannerfall-backup`) and check that the file is there
3. `git fetch --tags origin && git checkout v1.3.1`, then either pull the image below or build it yourself with `--build-arg VERSION=1.3.1`; set `BANNERFALL_IMAGE` in `.env` to it and start it (`docker compose -f compose.prod.yaml up -d`). The database and Caddy keep running
4. Check the log for the migration (schema version 34), then `bannerfall-admin status` (version 1.3.1) and `bannerfall-admin check`

Going back to 1.3.0 works with the old image alone: 1.3.0 doesn't know the new table and leaves it alone. Starting 1.3.1 again later keeps the table as it was, without the reports sent under 1.3.0 in between. To remove it as well, restore the backup from step 2 (play since the update is lost).
